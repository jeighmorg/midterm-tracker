# CLAUDE.md

Guidance for Claude Code when working in this repository.

## What this is

An interactive US midterm-elections tracker: district/state maps colored by partisan lean and race ratings, a 270toWin-style scenario builder (click a seat to flip its projected winner and watch the seat count recompute), and small widgets for generic ballot, presidential approval, inflation, and unemployment. Personal project, meant to be shareable via a public link, built to run at $0/month.

## Stack

React + TypeScript + Vite + Tailwind. Mapping via `react-simple-maps` (wraps `d3-geo`/`topojson-client`). Deployed to Netlify's free tier.

**Map projection gotcha:** `us-atlas` ships both unprojected (`states-10m.json`) and pre-projected (`states-albers-10m.json`) topology. `ComposableMap projection="geoAlbersUsa"` expects the *unprojected* file — feeding it the pre-projected one double-projects coordinates and renders garbage (hit this once already; see git history).

**Sign convention gotcha:** `partisanLean` is always D-positive (positive = more Democratic) — `ratingFromLean()` in `src/types/election.ts` must NOT flip its sign. It did once (assumed R-positive input, a holdover from the original placeholder data's inverted convention) and silently colored all 282 non-competitive House districts backwards — Wyoming showed "Safe D", San Francisco showed "Safe R" — while looking plausible enough at a glance to ship. See git history for the fix; if a future change to this function makes Wyoming's district look blue, that's this bug again.

## Current state

- **House map is district-level**, using real 119th Congress (2025-2027) boundaries from the Census Bureau's cartographic boundary file `cb_2024_us_cd119_20m`, converted to TopoJSON via `mapshaper` and filtered to the 435 voting districts (DC/PR non-voting seats dropped). File: `src/data/congressional-districts-119.json`, parsed in `src/data/districtTopology.ts`.
  - **Redistricting-currency caveat:** several states redrew congressional maps mid-decade in 2025 (litigation-driven, e.g. TX/MO/NC/OH/CA and others). This snapshot reflects what Census had on file when `cb_2024_us_cd119_20m` was published. Before relying on this for real 2026 race calls, verify against a currently-maintained source (Dave's Redistricting App is actively updated for exactly this kind of mid-decade change) and re-run the conversion pipeline below if boundaries have moved. Don't hand-patch specific states from memory — verify against a live source first.
  - To refresh: download the current `cb_YYYY_us_cd119_20m.zip` from `https://www2.census.gov/geo/tiger/GENZYYYY/shp/`, then `mapshaper -i <shp> -filter 'STATEFP!="11" && STATEFP!="72"' -filter-fields STATEFP,CD119FP,GEOID -o format=topojson congressional-districts-119.json`, drop into `src/data/`.
- Senate map stays state-level (`src/components/map/USMap.tsx`) — correct, since Senate seats are per-state.
- `houseSeats` per state and `TOTAL_HOUSE_DISTRICTS` (435) are derived from the real district topology, not hand-typed — so they'll self-correct if the topology file is refreshed.
- Scenario builder: House view flips individual districts, Senate view flips individual states; both recompute their seat tally live. Toggle "Scenario mode" to enable clicking.
- **House map has zoom controls** (`DistrictMap.tsx`, react-simple-maps' `ZoomableGroup`, capped at 8x — the topology's 20m generalized resolution doesn't reveal more past that) — +/-/reset buttons plus free scroll-wheel zoom and drag-pan from the same component. District borders use `vectorEffect="non-scaling-stroke"` so they stay a constant width when zoomed instead of thickening. Senate map (`USMap.tsx`) doesn't have this — states are large enough not to need it, and it wasn't asked for there.
- **Hover tooltips** show the district/state name, rating, top two candidates (name + party + real FEC fundraising total where matched), and — on the Senate map only — statewide presidential approval where polled. Built from `useHoverTooltip.ts` (tracks hovered id + cursor position) and `MapTooltip.tsx` (presentational), used by both `DistrictMap.tsx` and `USMap.tsx`. Deliberately shows the categorical rating (Safe/Likely/Lean/Tossup) as-is rather than inventing a numeric win probability — no source we use publishes real probabilities, only categorical ratings; see the candidates fetchers below for the one further-afield case where a probability-style forecaster's number could theoretically be added (it isn't, on purpose). State approval renders independent of whether that state has a 2026 Senate race (Wisconsin shows approval with "No Senate race in 2026" right alongside it) — the two data sources are unrelated and the tooltip treats them that way.
- **The Senate tally is full-chamber control (100 seats), not just the 35 up in 2026.** `SENATE_FIXED_SEATS` (`stateRaceData.ts`, sourced from `generated/senate-composition.json`) holds the real current party of the 65 seats not on the ballot this cycle; `App.tsx` seeds the tally with those (bucketed as `safe-d`/`safe-r`, since they can't change this cycle) before adding the scenario-adjustable 35. Majority line is at 51/100.
- **Control needles** (`ControlNeedle.tsx`, between the seat tallies and the indicator widgets) are NYT/270toWin-style gauges for House and Senate control. There is no real probabilistic model backing them (same reason as the tooltips) — the needle position is a transparent, deterministic function of the same `seatsByRating` tally already shown in the bar above: each rating maps to a rough win probability (Safe=95%/5%, Likely=80%/20%, Lean=65%/35%, Tossup=50%), summed into an "expected seats" figure (the standard way forecasters turn categorical ratings into one number), then compared against the majority threshold and normalized against `LANDSLIDE_FRACTION` (15% of the chamber) as the "fully deflected" reference. **First real computation landed both chambers at genuine toss-up** (House expected ~217 of 435, Senate ~50 of 100) despite the seat-tally bar showing D ahead in both — this is not a bug, and not a contradiction either: the bar counts "which party currently leads," the needle asks "how much does that lead survive once you discount for how uncertain the lean/tossup seats really are," and those can legitimately differ. Verified interactively that flipping seats in scenario mode moves the needle live (dispatched synthetic clicks on 30 safe-R districts → House needle swung from ~1° to ~53° toward D, label flipped from Toss-up to "Lean D control").

## Data pipeline (phase 2 — implemented)

`scripts/fetch-*.mjs` (run via `npm run fetch-data`, or individually) pull real data and write it to `src/data/generated/*.json`, which the app imports directly at build time. No server, no database. One fetcher (fundraising, below) needs an API key; everything else needs none.

**Source choice: Wikipedia, not the rating sites directly.** The original plan was to scrape Cook Political Report / Sabato / Inside Elections / 270toWin pages individually, which raised real ToS/legal-gray-area questions. Instead, Wikipedia's `2026 United States House of Representatives election ratings` and `2026 United States Senate elections#Predictions` pages already aggregate all of those raters (plus DDHQ, Silver Bulletin, The Economist, etc.) into one cited, wikitext table per race, updated frequently. Same for generic ballot and presidential approval polling averages (`2026 United States House of Representatives elections#Opinion_polling` and `Opinion polling on the second Trump presidency`). Pulling from Wikipedia's MediaWiki API (explicitly designed for programmatic read access, no auth, generous rate limits) is both lower-risk and lower-maintenance than running four+ separate scrapers against sites that weren't built to be scraped.

- `scripts/fetch-house-ratings.mjs` → `generated/house-ratings.json`: parses the House ratings wikitable, computes a consensus rating per district by averaging each rater's `{{USRaceRating}}` into a signed score (R positive) and re-bucketing into our 7-point scale. **Only covers the ~150 districts at least one rater considers competitive** — this is a real, current limitation, not a bug.
- `scripts/fetch-district-pvi.mjs` → `generated/district-pvi.json`: parses the *full* 435-district Cook PVI table from the "Cook Partisan Voting Index" Wikipedia article ("By congressional district" section) — same `{{ushr}}`/`{{Shading PVI}}` templates as the ratings tables, but spelled-out state names instead of USPS codes, so it needs its own extractor (`extractDistrictByStateName`). This closes the full-district gap: `districtRaceData.ts` uses the rater-consensus rating where one exists (competitive seats) and falls back to `ratingFromLean(cookPvi)` for the rest — **every district now has real data, no placeholder/jitter left**. Watch for `{{Shading PVI|R|value=7}}`-style named parameters mixed in with the usual positional `{{Shading PVI|R|7}}` — `extractPvi` in `lib/ratings.mjs` strips a `value=` prefix to handle both.
- `scripts/fetch-senate-ratings.mjs` → `generated/senate-ratings.json`: same approach, but the Senate table lists **every** 2026 race (not just competitive ones), so this has full real coverage — including special elections a hand-typed "Class 2 states" list would miss (this caught FL and OH, which aren't regular Class 2 seats).
- `scripts/fetch-senate-composition.mjs` → `generated/senate-composition.json`: parses "List of current United States senators" (the "List of senators" table) for the real party of the 65 seats NOT up in 2026 — this is what turns the Senate tally into a full 100-seat control tracker instead of just the 35 contested races. Two things worth knowing: (1) the table gives 2 rows per state via `rowspan`, so state identity isn't needed at all — each row is independently classified by party template and by whether its "next election" link says `|2026]]`; (2) Minnesota's senators are formatted as "Democratic–Farmer–Labor Party", not "Democratic" — `normalizeParty()` handles that alongside Independents (Sanders, King), who are counted with the Democratic caucus they sit in, matching standard "who controls the Senate" reporting. The script hard-fails if it doesn't find exactly 100 senator rows, since that would mean the table structure changed. As a cross-check, its up-in-2026 count independently matched `senate-ratings.json`'s 35 exactly.
- `scripts/fetch-generic-ballot.mjs` / `scripts/fetch-approval.mjs` → `generated/generic-ballot.json` / `generated/approval.json`: parse the pre-computed "Average" row of each polling-aggregator table.
- `scripts/fetch-state-approval.mjs` → `generated/state-approval.json`: parses the same approval Wikipedia article's "Statewide job approval ratings" section, one wikitable per state. **Only 17 states get individually polled** — this is the real number, not a bug or a partial scrape; most states just never get statewide presidential-approval polling. Picks the row with the latest year when a state has more than one poll (observed: every state currently has exactly one, but don't rely on that). Surfaces in the Senate map tooltip only, independent of whether that state has a 2026 race.
- `scripts/fetch-fundraising.mjs` → `generated/fundraising.json`: real FEC candidate financial totals (receipts/disbursements/cash-on-hand), matched to the candidate names already in `house-candidates.json`/`senate-candidates.json`. **The one fetcher that needs an API key** (`FEC_API_KEY` — a free, instant, no-approval signup at api.data.gov/signup; set as a GitHub Actions repo secret, passed through in `update-data.yml`'s `env:`). Skips gracefully with a log line if the key isn't set, so local `npm run fetch-data` still works without it.
  - One call per race via FEC's `/candidates/totals/` endpoint (filtered by state/district/office/cycle) — this endpoint embeds each candidate's totals directly, so no separate search-then-totals round trip is needed. ~470 calls total (435 House + 35 Senate).
  - **Rate limit gotcha:** FEC's documented default is 1000 requests/hour per key, but the real limit encountered was much stricter — a 250ms delay between calls triggered constant 429s. Backed off to `DELAY_MS = 1000` (1 req/sec) in `fetch-fundraising.mjs`, which ran clean with zero 429s. If this fetcher starts timing out or erroring in CI, check for 429s in the log before assuming something else broke.
  - Name matching (`matchFecCandidate` in `lib/fec.mjs`) is last-name-primary, not full-name: FEC's "LAST, FIRST" format doesn't reliably match ours ("First Last") on nicknames (hit this with "Dave Flippo" vs FEC's "DAVID" — required loosening from a strict first+last match). First name / highest-receipts only used to disambiguate the rare case of two same-surname candidates in one race. First real run: House 824/867 candidates matched (95%), Senate 67/68 (98%).
- `scripts/fetch-economic.mjs` → `generated/economic.json`: FRED's public CSV export (`fredgraph.csv?id=...`), no API key needed. Uses `CPIAUCNS` (not seasonally adjusted) for the 12-month CPI change, matching BLS's standard headline inflation figure, and `UNRATE` for unemployment.
- `scripts/fetch-house-candidates.mjs` / `scripts/fetch-senate-candidates.mjs` → `generated/house-candidates.json` / `generated/senate-candidates.json`: candidate names + party, powering the hover tooltips. Different data shape entirely from the ratings fetchers — these parse `{{Infobox election}}` templates (`candidate1`/`nominee1`/`party1`/`candidate2`/`nominee2`/`party2` — Wikipedia uses both field names inconsistently across articles, `lib/infobox.mjs` checks both) out of each **state's own election article**, not a shared ratings table:
  - House: 50 requests, one per state's "2026 United States House of Representatives elections in {State}" article (plural title; districts are `==District N==` subsections, each with its own infobox). At-large states (AK/DE/ND/SD/VT/WY) instead have a singularly-titled "...election in {State}" article (no "s", no district subsections) — hardcoded in `AT_LARGE_STATES` since it's fixed for this apportionment cycle.
  - Senate: 35 requests, one per state's "2026 United States Senate election in {State}" article — except FL and OH, which are special elections and use "...Senate special election in {State}" instead (`SPECIAL_ELECTION_STATES`). The 35-state list itself comes from `senate-ratings.json` at fetch time rather than being hardcoded again.
  - Both fail soft per-state (log and skip) rather than aborting the whole run, and got 435/435 districts and 34/35 states with at least one candidate on first real run (the missing one, Delaware, genuinely has no confirmed nominees yet — not a parsing failure).
  - **Do not add a numeric "win probability" field here.** No source in this pipeline publishes one (see "Current state" above) — showing the categorical rating is the honest representation of what we actually have.
- `scripts/lib/wikitext.mjs`'s `cellValue()` is the key parsing trick for the *table*-shaped sources (ratings, polling, composition): wikitable cells are written as `attribute|value` or `{{template}} |value` — the actually-displayed value is reliably whatever comes after the **last** `|` in the cell. The infobox-shaped sources (candidates) are simpler — `key = value`, one per line — but watch for a wikilink's own internal `|` ([[Target|Display]]): capture to end-of-line, not to the first `|`, or you'll truncate every piped display name (hit this once; see git history).
- Parsers skip header/footer rows gracefully (logged as a count, not an error) rather than crashing — wikitext table structure is inherently a little fragile, so failing soft beats a broken build.
- `scripts/lib/wikipedia.mjs` retries 429/5xx with backoff (honoring `Retry-After`), and `fetch-all.mjs` sleeps 1s between tasks — six real Wikipedia calls back-to-back will otherwise trip their rate limiter (hit this once; see git history).

**Refreshing data:** `npm run fetch-data` runs all eleven fetchers and overwrites `src/data/generated/*.json`. Order matters for three of them: the two candidate fetchers run after the ratings fetchers (need no upstream data, just placed late since they're the next-slowest at ~85 requests combined) and `fundraising` runs last of all since it reads the candidate files and is by far the slowest (~470 requests, ~8 min at the 1s pacing above). `.github/workflows/update-data.yml` runs this weekly (Mondays 12:00 UTC) via GitHub Actions and commits any changes as `github-actions[bot]`, which triggers a Netlify redeploy. Live at https://github.com/jeighmorg/midterm-tracker, deployed at https://midterm-tracker-2026-jm.netlify.app/ — verified working end-to-end via a manual `workflow_dispatch` run.

7. ~~FEC fundraising~~ — done: see `fetch-fundraising.mjs` above.
8. **Per-race general-election polling for the hottest Senate/House races** — investigated, not built. Each Senate race's own Wikipedia page (e.g. "2026 United States Senate election in North Carolina") has a real "Polling" section under "General election" with actual head-to-head numbers, not just a categorical rating. House races have the same structure but far sparser coverage (spot-checked Nevada: 1 of 4 districts had a Polling section). Would need per-race page fetches (33-35 for Senate, an unknown and much smaller subset of the 435 for House) — bigger lift than the other additions here for narrower payoff.
9. **Scenario builder polish** — encode scenario state in the URL (shareable links, 270toWin-style).
10. **Indicator widgets** — small trend charts (sparklines) instead of single numbers; both generic-ballot and approval sources actually carry per-aggregator history that could be plotted.
11. **Polish** — mobile layout, legend, zoom/pan for dense urban districts, dark mode (Tailwind `darkMode: 'media'` already configured), an About/Methodology page crediting every data source (important once this is a public link) — Wikipedia's CC BY-SA license means the page should credit it and, ideally, link back to the specific articles pulled from.

## Maintenance model

Weekly fetch runs unattended via GitHub Actions once pushed to GitHub. Manual work is limited to: noticing if a parser silently breaks (Wikipedia table structure changed — the pipeline logs a skipped-row count per run, worth spot-checking after any big edit war on the source pages), double-checking marquee races near election day since a weekly cadence lags fast-moving calls, and periodically re-verifying district boundaries in any state under active redistricting litigation.
